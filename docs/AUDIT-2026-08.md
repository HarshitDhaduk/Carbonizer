Read-only audit of `HarshitDhaduk/Carbonizer` @ `f2dc53a`, across five dimensions:
code quality, security, efficiency, testing, accessibility.

Findings are ranked by severity. Every entry cites `file:line`. Fixes applied on
`audit/2026-08-hardening` are marked **[fixed]**; items whose only correct fix
would change a public API, route, env var, config shape or data format are
marked **[recommendation]** and were deliberately left in place.

## Critical

### C1 — CORS trusts every `*.vercel.app` / `*.onrender.com` origin, with credentials **[fixed]**

`backend/app/main.py:104-119`

```python
_PROD_ORIGIN_REGEX = (
    r"https://[a-z0-9-]+\.vercel\.app"
    r"|https://[a-z0-9-]+\.onrender\.com"
)
app.add_middleware(CORSMiddleware, allow_credentials=True,
                   allow_origin_regex=_PROD_ORIGIN_REGEX if settings.is_production else ...)
```

Starlette matches this with `re.fullmatch` (`starlette/middleware/cors.py:102`),
so *any* subdomain on either platform satisfies it. Both platforms hand out
free subdomains on signup, so the allowlist is effectively "anyone who wants in".

Reproduced against the app in production mode:

```
https://evil-attacker.vercel.app             -> ACAO='https://evil-attacker.vercel.app'      ACAC='true'
https://totally-not-carbonizer.onrender.com  -> ACAO='https://totally-not-carbonizer...'     ACAC='true'
https://carbonizer.vercel.app                -> ACAO='https://carbonizer.vercel.app'         ACAC='true'
https://evil.example.com                     -> ACAO=None                                    ACAC='true'
```

With `Access-Control-Allow-Credentials: true` and prod cookies at
`SameSite=None` (`config.py:112-118`), an attacker page on such an origin can
read authenticated responses for any victim holding a session on the API origin:

* **Data theft via GET.** GETs are CSRF-exempt by design (`core/csrf.py:60-61`),
  so `/footprint/summary`, `/community/benchmark`, `/connections`,
  `/privacy/settings`, `/privacy/consents`, `/auth/me` and the entire
  `GET /privacy/export/{job_id}/download` personal-data bundle
  (`api/v1/privacy.py:101-142`) are all readable cross-origin.
* **Account takeover.** `POST /auth/refresh` is on the CSRF exemption list
  (`core/csrf.py:44-48`) *and* returns a live access JWT in its body
  (`api/v1/auth.py:225` → `_token_response`, `auth.py:60-63`). The attacker page
  can call it with `credentials: 'include'` and read the token out of the
  response — a bearer credential for the victim's account.

The comment at `main.py:100-103` argues the CSRF double-submit contains this
("a malicious vercel.app project can't drive the API even with a matching
origin"). That reasoning does not hold: it covers neither GETs nor the
CSRF-exempt refresh route.

**Fix applied.** The preview-origin pattern is now derived from the hostnames
already configured in `CORS_ORIGINS`, so previews of *this* project keep
working and unrelated projects on the same platform do not. `CORS_ORIGINS`
entries continue to be honoured verbatim. No env var, route, or response shape
changed.

## High

### H1 — `/auth/refresh` re-issues sessions for erased users **[fixed]**

`backend/app/api/v1/auth.py:204-225`

The handler decodes the refresh JWT and immediately calls `set_auth_cookies` —
it never checks that the subject still exists. Login does filter deleted users
(`auth.py:188`, `User.deleted_at.is_(None)`), and `dsr._purge_user`
(`services/dsr.py:150-184`) hard-deletes the row on erasure, but tokens are
stateless with no denylist. A refresh cookie issued before a GDPR erasure keeps
minting valid 15-minute access tokens for the remaining 30 days.

**Fix applied.** When a DB session is available and the subject parses as a
UUID, `/auth/refresh` now verifies a non-deleted user row exists before
re-issuing, and 401s otherwise. Seed mode and the demo subject are unchanged;
valid users see no difference.

### H2 — Next.js app ships no security response headers **[fixed]**

`frontend/next.config.mjs:18-34`

`nextConfig` has no `headers()`. The origin that renders HTML and holds the
session cookies serves no `X-Frame-Options`/`frame-ancestors` (clickjacking),
no `Referrer-Policy`, no `X-Content-Type-Options`, and no `Permissions-Policy`.

The backend's own module docstring asserts otherwise —
`backend/app/core/security_headers.py:8-9`: *"The Next.js frontend ships its own
CSP via next.config.mjs (different needs because it serves HTML)."* It does not.
The API is hardened; the app in front of it is not.

**Fix applied.** Added a `headers()` block covering all routes. The CSP is
restricted to directives that cannot break Next's inline runtime —
`frame-ancestors`, `base-uri`, `form-action`, `object-src` — alongside the four
unambiguous headers. A `script-src`/`style-src` policy needs Next's nonce
plumbing and is left as a follow-up (see recommendations).

### H3 — Vulnerable `cryptography` pin **[fixed]**

`backend/requirements.txt`, `backend/pyproject.toml`

`cryptography==48.0.1` carries three advisories (PYSEC-2026-3552 / -3553 /
-3554), fixed in 49.0.0 and 50.0.0. This is not an incidental build dependency:
it is the library behind `app/core/crypto.py`, which envelope-encrypts every
stored provider access token (`connections.access_token_enc`).

**I missed this in the read-only pass** — the first draft of this report was
written from source review alone, without running `pip-audit` / `npm audit`.
CI's own dependency gate caught it. That is a gap in the audit method, not just
in the code: a source-only review cannot see a dependency advisory published
after the pin was chosen. Both audits are now part of the checklist below.

**Fix applied.** Bumped to `cryptography==50.0.0` in both `requirements.txt`
and `pyproject.toml` (kept in sync per the note now at the top of the former).
Verified safe rather than assumed:

* the full backend suite passes against it;
* a `cp311-abi3` manylinux wheel exists, so CI's Python 3.11 gets a binary and
  the Docker build needs no new toolchain;
* the Fernet wire format is unchanged — version byte still `0x80` — so
  ciphertext already in Postgres still decrypts. A new frozen-ciphertext test
  (`test_fernet_ciphertext_stays_readable_across_library_upgrades`) pins this,
  so a future bump that *did* change the format fails loudly instead of
  silently orphaning every connected account's token.

`pip-audit --requirement requirements.txt --strict` now reports
`No known vulnerabilities found`.

### H4 — `next@16.2.9` carries nine advisories **[fixed]**

`frontend/package.json`

`npm audit` initially surfaced `postcss` and `sharp` — build-time tooling whose
advisories need attacker-controlled CSS or images, neither of which this app
processes. On that basis I first recorded the whole `npm audit` failure as a
low-risk Dependabot item.

**That call was wrong, and it was wrong because I read a truncated `tail` of the
audit output rather than the whole report.** The full output lists a ninth entry
that matters much more: `next` itself, `16.0.0 - 16.2.10`, with nine advisories.
Several map directly onto surfaces this app uses:

* **GHSA-p9j2-gv94-2wf4** — SSRF in rewrites via attacker-controlled destination
  hostname. This app rewrites `/api/v1/:path*` in both `next.config.mjs` and
  `vercel.json`.
* **GHSA-68g3-v927-f742** / **GHSA-4633-3j49-mh5q** — cache confusion of response
  bodies for requests with bodies. The dashboard serves per-user data under
  `Cache-Control: private` (`app/core/cache.py`); cross-served bodies here mean
  one user's footprint rendered for another.
* **GHSA-6gpp-xcg3-4w24** — middleware / proxy bypass in App Router under
  Turbopack, which is this project's build path.
* **GHSA-955p-x3mx-jcvp** — unauthenticated disclosure of internal Server
  Function endpoints.

**Fix applied.** `next` 16.2.9 → 16.3.0 (with `eslint-config-next` and
`@next/bundle-analyzer` moved in step, and the direct `postcss` devDependency
range lifted to `^8.5.26` so the weekly all-severity audit is clean too).

A targeted `overrides` block pinning only `postcss` and `sharp` was tried first
and rejected: it cleared those two but left the nine `next` advisories, which
were the ones that actually mattered. `next@16.3.0` pulls patched `postcss`
(8.5.23) and `sharp` (0.35.3) transitively, so no overrides are needed and the
final diff is four version bumps.

Validated as a framework bump rather than assumed: `npm audit` → 0
vulnerabilities, prettier, eslint, `next build` (same 8 routes), `tsc --noEmit`,
vitest 75/75 with the coverage gate, all 15 Playwright specs including axe-core
on three routes, and a live check that the H2 security headers still land.

## Medium

### M1 — `/readyz` echoes raw driver exceptions to anonymous callers **[fixed]**

`backend/app/api/v1/health.py:55-56`

```python
except Exception as exc:
    db_ok = f"error: {exc}"
```

`/readyz` is unauthenticated (it's the Render health-check path,
`render.yaml:24`). Whatever asyncpg or SQLAlchemy raises is returned verbatim.
Reproduced with a deliberately broken DSN:

```
{"status":"degraded","database":"error: connect() got an unexpected keyword argument 'sslmode'"}
```

The class of disclosure tracks the failure mode: credential errors surface the
Postgres role name, TLS errors surface host and certificate detail, DSN errors
surface connection arguments.

**Fix applied.** The exception is logged server-side at WARNING with full
traceback; the response carries a generic `"error"` marker. The JSON shape
(`{"status", "database"}`, `database` still a string) and the 200/503 semantics
are unchanged.

### M2 — Documented per-email rate limiter does not exist **[fixed: docs + dead code]**

`backend/app/core/rate_limit.py:32-47`

`_email_key` is defined and never referenced. It reads
`request.state._login_form`, which nothing in the tree ever sets — verified:

```
$ grep -rn "_login_form\|_email_key" --include=*.py .
./app/core/rate_limit.py:32:def _email_key(request: Request) -> str:
./app/core/rate_limit.py:41:        body_form = getattr(request.state, "_login_form", None)
```

Two places advertise the protection anyway: the module docstring
(`rate_limit.py:5-9`, "**Credential stuffing** — many IPs against one known
email: bounded by the email limit") and the `/auth/login` OpenAPI description
(`api/v1/auth.py:153-154`, "on credential-stuffing patterns the email-scoped
limiter kicks in too"). Only the per-IP `5/minute` actually applies, which a
distributed stuffing run walks straight past.

Separately, `_client_ip`'s docstring (`rate_limit.py:28`) claims
`get_remote_address` "respects X-Forwarded-For when present". It does not
(`slowapi/util.py`); the real-IP resolution comes from uvicorn's
`--proxy-headers` flag in `backend/Dockerfile:47`.

**Fix applied.** Removed the dead helper and corrected all three docstrings so
they describe what the code does. Actually adding an email-scoped limiter
changes when callers receive 429 — see recommendations.

### M3 — Audit rows never capture the minted request id **[fixed]**

`backend/app/services/audit.py:58-60`

```python
req_id = request.headers.get("x-request-id") if request is not None else None
```

`RequestIdMiddleware` mints a UUID when the header is absent
(`core/request_id.py:41-42`), stores it in `request_id_var`, and echoes it on
the response — but never writes it back onto the request headers. So for any
request that doesn't arrive with an inbound `X-Request-Id` (i.e. every direct
call), the log lines and the response header carry an id while the audit row
stores `NULL` — defeating exactly the correlation the module promises
(`audit.py:51-53`).

**Fix applied.** `record` now reads `request_id_var` first and falls back to the
header. Column and schema unchanged.

### M4 — `download_export` skips the ownership check it documents **[fixed]**

`backend/app/api/v1/privacy.py:105-142`

The docstring says *"we re-verify the job belongs to them so a stolen job id
can't be replayed against another account"* (`privacy.py:113-116`). The handler
never loads `DsrJob`. `job_id` is accepted unvalidated, and is written into the
audit log as `resource_id` (`privacy.py:130`).

The bundle itself is keyed on `subject`, so this is **not** a cross-user data
leak. The defects are real but narrower: a request naming a nonexistent or
another user's job returns 200, and the audit trail can be stuffed with
arbitrary UUIDs that never corresponded to a real export.

**Fix applied.** The handler now loads the job and requires it to exist, be an
export, and belong to the caller — 404 otherwise. Safe because
`dsr_export.create_export_job` (`services/dsr_export.py:32-45`) always inserts
the row before handing out the URL, so every legitimate download URL resolves.
Note this does change the status code on the error path (200 → 404) for an id
no legitimate client can produce.

### M5 — Aggregations materialize full ORM entities **[fixed]**

`backend/app/services/bank_sync.py:142-155`, `:162-174`;
`backend/app/services/attribution.py:54-60`

```python
tx_res = await db.execute(select(RawTransaction).where(...))
for txn in tx_res.scalars().all():
    gbp = txn.amount_minor / 100
```

Every footprint recompute loads each `RawTransaction` and `RawEnergyRead` in
the 84-day window as a fully instrumented mapped instance — identity map entry,
attribute instrumentation, all columns — in order to sum four floats. The
sandbox provider alone generates ~168 energy reads per sync
(`services/providers.py:146-158`), and this runs on every `/connections/*/link`
and `/sync`.

**Fix applied.** These three queries now select only the columns they read.
Return types and computed values are identical.

### M6 — Refresh flow is dead code; sessions expire after 15 minutes **[fixed]**

`frontend/src/lib/client-api.ts:154`

```
$ grep -rn "clientApi.refresh" src/
(no matches)
```

The whole refresh mechanism is built and unused: the 30-day refresh cookie
(`core/cookies.py:74-83`), its `Path=/api/v1/auth` scoping, the rotation
endpoint (`api/v1/auth.py:199-225`), and the client method. Nothing calls it.
In practice the access cookie expires after `access_token_ttl_minutes` (15,
`core/config.py:42`), the next `/auth/me` 401s, and `useAuthGuard`
(`src/lib/use-auth-guard.ts:26-28`) bounces the user to `/onboarding` — a
forced re-login every 15 minutes despite a valid 30-day session.

`clientApi.ensureCsrf` (`client-api.ts:150`) is likewise never called, though
both it and the endpoint (`api/v1/auth.py:270-274`) state the frontend calls it
at boot. This one is benign — login/register/refresh are CSRF-exempt and set the
cookie — but the documented contract isn't what happens.

**Fix applied.** `request()` now retries once through `/auth/refresh` on a 401,
skipping the auth endpoints themselves to avoid recursion. Contained entirely
within `client-api.ts`; the exported `clientApi` surface is unchanged.

### M7 — Modal dialog has no focus trap and no focus restore **[fixed]**

`frontend/src/components/ui/ConfirmDialog.tsx:33-41`

The dialog sets `role="alertdialog"` and `aria-modal="true"` — asserting the
rest of the page is inert — but nothing enforces it. Tab from the confirm button
walks straight out into the page behind the overlay, and on close focus is
dropped to `<body>`, so a keyboard or screen-reader user restarts from the top
of the document. WCAG 2.4.3 (Focus Order). This gates logout
(`components/layout/AccountMenu.tsx:70-78`).

**Fix applied.** Tab and Shift+Tab now cycle within the dialog, and focus
returns to the element that opened it on close. Props are unchanged.

### M8 — Radio group is not keyboard-operable as a radio group **[fixed]**

`frontend/src/components/onboarding/QuestionInput.tsx:58-79`

`role="radiogroup"` wrapping `role="radio"` buttons with `aria-checked` gives
assistive tech an explicit contract: one tab stop, arrow keys move and select.
Neither holds — every option is its own tab stop and arrow keys do nothing. This
is the primary control of the onboarding flow (5 of 8 questions are
single-choice, `services/questionnaire.py:28-89`).

**Fix applied.** Roving `tabIndex` plus Arrow/Home/End handling per the ARIA
radio-group pattern. Component props unchanged.

### M9 — Slider's accessible name doesn't say what it measures **[fixed]**

`frontend/src/components/onboarding/QuestionInput.tsx:115`

```jsx
aria-label={unit ? `Value in ${unit}` : "Value"}
```

A screen-reader user tabbing to the "How far do you drive a week?" step hears
"Value in km, slider, 100" — the question text lives in the `<legend>`, which
is not reliably announced as the control's name.

**Fix applied.** The question label is threaded down and used as the accessible
name; the unit stays in `aria-valuetext`.

### M10 — Questionnaire step changes are silent to screen readers **[fixed]**

`frontend/src/components/onboarding/Questionnaire.tsx:84-105`

Pressing "Next" swaps the question in place. There is no live region and focus
stays on the Next button, so a screen-reader user gets no indication the content
changed — the same failure mode as an unannounced SPA route change.

**Fix applied.** Added a polite live region announcing "Question N of M: label"
on each step change.

### L3 — `dispose_engine` leaves a stale sessionmaker **[fixed]**

### L4 — Seed-mode credential check is not constant-time **[fixed]**

`backend/app/api/v1/auth.py:174` compares the demo password with `!=`.

### L5 — `/ingest/*` is unauthenticated and unbounded **[recommendation]**

`backend/app/api/v1/ingest.py:28,40,51`. The module docstring promises
*"Authenticated machine-to-machine in production (HMAC signature header)"*;
there is no auth dependency on any of the three routes, and `list[TransactionIn]`
carries no size bound, so an anonymous caller can force arbitrarily large
Pydantic parses. The handlers are no-ops today (they count items and return),
which caps the blast radius at CPU/memory. Both fixes — adding auth, and
rejecting oversized batches — change the contract for existing callers, so
neither is applied. Docstring corrected to stop claiming auth that isn't there.

### L6 — Dead code and references to files that don't exist **[fixed]**

* `frontend/src/lib/client-api.ts:5` points at `src/lib/api.ts` — no such file.
* `backend/app/core/config.py:64` points at
  `python -m app.scripts.gen_encryption_key` — no such module. The working

* `backend/app/core/config.py:65-66` says an empty `ENCRYPTION_KEY` "falls back

All three corrected.

### L7 — `readyz` test is not hermetic **[fixed]**

`backend/tests/test_api.py:515`. `conftest.py:24` overrides the `get_db`
dependency, but `readyz` reads `settings.use_db` and calls `get_engine()`
directly (`api/v1/health.py:49-53`), bypassing the override. A developer `.env`
with `USE_DB=true` fails the test — this is the one failure in the baseline.
**Fixed:** the test now pins `settings.use_db` for each branch, so both the
seed-mode and DB-unreachable paths are covered deterministically.

### L8 — Nav rail labels never become visible for keyboard users **[fixed]**

`frontend/src/components/layout/NavRail.tsx:19,45`. The rail expands and reveals
labels on `hover:` only, so a keyboard user tabbing through primary navigation
sees icons with no visible text at any point. The accessible names are present
(the spans are `opacity-0`, not `display:none`), so this is a visual affordance
gap rather than a screen-reader one. **Fixed:** added `focus-within` variants
alongside the hover ones.

## Recommendations not applied (would be breaking)

1. **Token revocation.** JWTs are stateless with no denylist, so `/auth/logout`
   (`api/v1/auth.py:233-260`) and GDPR erasure (`services/dsr.py:150`) can't
   invalidate an outstanding refresh cookie. H1 closes the erasure hole for
   DB-backed users; a real fix needs a `jti` denylist table checked on refresh,
   which adds a schema migration and a per-refresh read.
2. **Per-email rate limiting** (M2). Adding a second limiter changes when
   callers receive 429, so it belongs in its own change with its own tests.
3. **`/ingest/*` authentication and batch bounds** (L5).
4. **Trusted proxy scope.** `backend/Dockerfile:47` runs uvicorn with
   `--forwarded-allow-ips=*`, so `X-Forwarded-For` is trusted from any upstream.
   Correct behind Render's proxy; if the instance ever becomes directly
   reachable, an attacker can rotate that header to get a fresh rate-limit
   bucket per request. Pin to the platform's proxy range when it's known.
5. **Multi-replica rate limiting.** The slowapi store is in-memory
   (`core/rate_limit.py:52`), so limits are per-process. `RATE_LIMIT_STORAGE_URL`
   already exists as the seam; a second replica silently doubles every limit.
6. **Full CSP on the frontend.** H2 adds the directives that are safe without
   nonce plumbing. A `script-src`/`style-src` policy needs Next's nonce support
   wired through middleware and should be validated route by route.
7. **`_demo_settings` is process-global mutable state.**
   `backend/app/api/v1/privacy.py:27-31` — `GET /privacy/settings` returns one
   shared object for every user. `PATCH` happens to be non-mutating
   (`privacy.py:61-63` builds a copy), so today it's a read-only demo fixture,
   but it is one line away from cross-user state bleed. Persisting to
   `privacy_settings` is the real fix and changes behaviour.
8. **Frontend coverage floor.** `frontend/vitest.config.ts:42-45` sets
   statements/lines at 7%. The comment is candid about why (components are
   covered by Playwright + axe rather than vitest) and names the follow-up. It
   remains the weakest gate in CI.
## Method note

Both `pip-audit` and `npm audit` should be run as part of any future pass over
this repo, and their output should be **read in full**. Two lessons from this
audit, recorded because both were process failures rather than code ones:

1. **H3 was found by CI, not by the review.** The first draft of this report was
   written from source review alone. A source-only pass cannot see an advisory
   published after a pin was chosen — `cryptography==48.0.1` looked fine in the
   diff and was not.
2. **H4 was initially misjudged from truncated output.** I read a `tail` of
   `npm audit`, saw only `postcss` and `sharp`, correctly reasoned they were
   low-risk build tooling, and filed the whole failure as a Dependabot item. The
   `next` entry — nine advisories including SSRF-in-rewrites on an app that uses
   rewrites — was above the cut. Piping a security tool through `tail` and
   concluding from what survives is how a real finding gets dismissed.
